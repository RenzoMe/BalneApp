1. ¿Qué es Room?
Room es una biblioteca de Android que permite guardar datos de manera persistente en una base de
datos SQLite utilizando Kotlin. Facilita las operaciones de consulta, inserción, actualización y
eliminación de datos, evitando escribir SQL repetitivo para muchas tareas comunes.
Por otro lado, Jetpack Compose es el sistema moderno de Android para construir interfaces gráficas
mediante funciones Kotlin.
Ambas tecnologías trabajan juntas, pero cumplen funciones distintas:
Capa
Función
Jetpack Compose
Muestra la información y recibe las acciones del usuario.
ViewModel / Repository
Organiza la lógica y coordina el acceso a los datos.
Room
Administra las operaciones de la base de datos SQLite.
El flujo entre capas: Compose envía eventos hacia abajo (ViewModel/Repository, luego Room) y
recibe estado hacia arriba.
¿Para qué sirve Room?
 Guardar información aunque se cierre la aplicación.
 Consultar datos sin depender de Internet.
 Modificar o eliminar registros.
 Modelar relaciones entre tablas.
 Observar cambios en los datos y actualizar la interfaz.
 Reducir errores al trabajar con consultas SQL.
Ejemplo: una aplicación de tareas puede utilizar Compose para mostrar una lista, Room para
guardar las tareas y un ViewModel para coordinar las operaciones.
2. Conceptos fundamentales de Room
Room se apoya en tres componentes principales.
1. Entity — la tabla
Representa una tabla de la base de datos. Cada objeto representa un registro y cada propiedad
representa una columna.
2. DAO — las operaciones
Significa Data Access Object. Define cómo insertar, consultar, actualizar y eliminar registros
mediante funciones Kotlin y consultas SQL.
3. RoomDatabase — la base de datos
Es la clase principal que conecta las entidades y los DAO con la base de datos SQLite.

3. Preparar el proyecto
En Android Studio, creá un proyecto con Kotlin y Jetpack Compose. Para utilizar Room, agregá sus
dependencias en el archivo de Gradle del módulo de la aplicación.
Ejemplo con Kotlin DSL (build.gradle.kts):
plugins {
    id("com.google.devtools.ksp")
}
dependencies {
    val roomVersion = "2.8.4"
    implementation("androidx.room:room-runtime:$roomVersion")
    implementation("androidx.room:room-ktx:$roomVersion")
    ksp("androidx.room:room-compiler:$roomVersion")
}
Este ejemplo supone que KSP ya está configurado para la versión de Kotlin del proyecto. Si no lo
está, hay que agregar el plugin compatible en el Gradle correspondiente. La versión de Room es un
ejemplo de referencia: conviene verificar la última versión estable y su compatibilidad con el
proyecto.
room-runtime proporciona la biblioteca principal; room-ktx integra las operaciones con corrutinas
y Flows; room-compiler, mediante KSP, genera el código necesario.

Paso 1. Crear la entidad (Tarea.kt)
import androidx.room.Entity
import androidx.room.PrimaryKey
@Entity(tableName = "tareas")
data class Tarea(
    @PrimaryKey(autoGenerate = true)
    val id: Int = 0,
    val titulo: String,
    val completada: Boolean = false
)
Explicación:
 @Entity: indica que la clase representa una tabla.
 tableName = "tareas": establece el nombre de la tabla.
 data class: permite representar datos de manera concisa.
 @PrimaryKey: define el identificador único de cada registro.
 autoGenerate = true: hace que SQLite genere los identificadores.
 completada: almacena si la tarea está terminada.
La tabla resultante tendrá tres columnas: id, titulo y completada.
Paso 2. Crear el DAO (TareaDao.kt)
import androidx.room.Dao
import androidx.room.Delete
import androidx.room.Insert
import androidx.room.Query
import androidx.room.Update
import kotlinx.coroutines.flow.Flow
@Dao
interface TareaDao {
    @Query("SELECT * FROM tareas ORDER BY id DESC")
    fun obtenerTodas(): Flow<List<Tarea>>
    @Insert
    suspend fun insertar(tarea: Tarea)
    @Update
    suspend fun actualizar(tarea: Tarea)
    @Delete
    suspend fun eliminar(tarea: Tarea)
}

insertar()
Guarda una tarea nueva.

Modifica una tarea existente.
eliminar()
Borra una tarea.

Paso 3. Crear la base de datos (AppDatabase.kt)
import android.content.Context
import androidx.room.Database
import androidx.room.Room
import androidx.room.RoomDatabase
@Database(
    entities = [Tarea::class],
    version = 1,
    exportSchema = false
)
abstract class AppDatabase : RoomDatabase() {
    abstract fun tareaDao(): TareaDao
    companion object {
        @Volatile
        private var INSTANCE: AppDatabase? = null
        fun obtenerInstancia(context: Context): AppDatabase {
            return INSTANCE ?: synchronized(this) {
                INSTANCE ?: Room.databaseBuilder(
                    context.applicationContext,
                    AppDatabase::class.java,
                    "tareas_db"
                ).build().also {
                    INSTANCE = it
                }
            }
        }
    }
}
Explicación de los elementos principales:
 @Database: declara la configuración de Room.
 entities: enumera las tablas de la base de datos.
 version = 1: establece la versión del esquema.
 tareaDao(): permite acceder a las operaciones.
 databaseBuilder(): construye la base de datos persistente.
 "tareas_db": nombre del archivo de la base de datos.
 INSTANCE: evita crear varias instancias innecesarias de la base de datos.
La base de datos se crea cuando se necesita, no hace falta construirla cada vez que el usuario abre
una pantalla.
En una aplicación de producción conviene exportar los esquemas y planificar las migraciones.
exportSchema = false se utiliza aquí para simplificar el ejercicio inicial.

Paso 4. Crear el repositorio (TareaRepository.kt)
El repositorio separa las operaciones de datos de la interfaz y del ViewModel.
class TareaRepository(
    private val dao: TareaDao
) {
    val tareas = dao.obtenerTodas()
    suspend fun agregar(titulo: String) {
        dao.insertar(Tarea(titulo = titulo))
    }
    suspend fun cambiarEstado(tarea: Tarea) {
        dao.actualizar(
            tarea.copy(completada = !tarea.completada)
        )
    }
    suspend fun borrar(tarea: Tarea) {
        dao.eliminar(tarea)
    }
}
El método copy() crea una nueva instancia de la tarea con el estado modificado, sin cambiar
directamente el objeto original.
Paso 5. Crear el ViewModel (TareaViewModel.kt)
import androidx.lifecycle.ViewModel
import androidx.lifecycle.ViewModelProvider
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.flow.SharingStarted
import kotlinx.coroutines.flow.stateIn
import kotlinx.coroutines.launch
class TareaViewModel(
    private val repository: TareaRepository
) : ViewModel() {
    val tareas = repository.tareas.stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),
        initialValue = emptyList()
    )
    fun agregar(titulo: String) {
        if (titulo.isBlank()) return
        viewModelScope.launch {
            repository.agregar(titulo.trim())
        }
    }
    fun cambiarEstado(tarea: Tarea) {
        viewModelScope.launch {
            repository.cambiarEstado(tarea)
        }
    }
    fun borrar(tarea: Tarea) {
        viewModelScope.launch {
            repository.borrar(tarea)
        }
    }
}

class TareaViewModelFactory(
    private val repository: TareaRepository
) : ViewModelProvider.Factory {
    override fun <T : ViewModel> create(
        modelClass: Class<T>
    ): T {
        if (modelClass.isAssignableFrom(TareaViewModel::class.java)) {
            @Suppress("UNCHECKED_CAST")
            return TareaViewModel(repository) as T
        }
        throw IllegalArgumentException("ViewModel desconocido")
    }
}
El ViewModel mantiene el estado que necesita la interfaz y ejecuta las operaciones mediante
corrutinas. Así evitamos realizar operaciones de base de datos en el hilo principal.
Paso 6. Crear la interfaz con Jetpack Compose (MainActivity.kt)
Este ejemplo asume que las clases anteriores están en el mismo paquete que la actividad.
import android.os.Bundle
import androidx.activity.ComponentActivity
import androidx.activity.compose.setContent
import androidx.activity.viewModels
import androidx.compose.foundation.layout.*
import androidx.compose.foundation.lazy.LazyColumn
import androidx.compose.foundation.lazy.items

import androidx.compose.runtime.*
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.unit.dp

class MainActivity : ComponentActivity() {
    private val viewModel: TareaViewModel by viewModels {
        val db = AppDatabase.obtenerInstancia(applicationContext)

        super.onCreate(savedInstanceState)
        setContent {
            MaterialTheme {
                PantallaTareas(viewModel)
            }
        }
    }
}

¿Qué sucede cuando agregamos una tarea?
1. El usuario pulsa Agregar tarea.
2. Compose llama a viewModel.agregar(titulo).
3. El repositorio llama al DAO, que inserta la tarea en Room.
4. El Flow emite la nueva lista y Compose actualiza la pantalla.
La clave es que no necesitamos volver a consultar manualmente las tareas después de cada
inserción: el flujo observado mantiene sincronizados los datos y la interfaz.
5. Consultas SQL con Room
Además de las operaciones básicas, podemos utilizar SQL para filtrar, ordenar y contar registros.
Supongamos que seguimos utilizando la tabla tareas.
Consultar tareas pendientes
@Query("SELECT * FROM tareas WHERE completada = 0")
fun obtenerPendientes(): Flow<List<Tarea>>
Buscar tareas por título
@Query("SELECT * FROM tareas WHERE titulo LIKE '%' || :texto || '%'")
fun buscarPorTitulo(texto: String): Flow<List<Tarea>>
El parámetro :texto recibe el valor que se quiere buscar. Room lo vincula de forma segura a la
consulta.
Contar las tareas completadas
@Query("SELECT COUNT(*) FROM tareas WHERE completada = 1")
fun contarCompletadas(): Flow<Int>
Eliminar todas las tareas
@Query("DELETE FROM tareas")
suspend fun eliminarTodas()
Estas funciones deben declararse dentro de la interfaz TareaDao. Room verifica las consultas
durante la compilación.

Diferencia entre suspend y Flow
Esta distinción suele generar confusión.
@Insert
suspend fun insertar(tarea: Tarea)
La función inserta un registro cuando se ejecuta. No devuelve automáticamente una lista
actualizada. En cambio:
@Query("SELECT * FROM tareas")
fun obtenerTodas(): Flow<List<Tarea>>
La función devuelve un flujo que emite listas y vuelve a emitirlas cuando cambian los datos
observados.
Regla práctica: usamos suspend para operaciones puntuales y Flow cuando queremos observar
datos que pueden cambiar.

Solución de la actividad 3
@Dao
interface AlumnoDao {
    @Insert
    suspend fun insertar(alumno: Alumno)
    @Query("SELECT * FROM alumnos")
    fun obtenerTodos(): Flow<List<Alumno>>

}
Solución de la actividad 5
Caso A: falta ejecutar la inserción dentro de una corrutina. Como insertar() es suspend, la
función que la llama también debe ser suspendible o invocarla desde una corrutina.
Caso B: falta definir una clave primaria. Una entidad de Room necesita una clave primaria, por
ejemplo @PrimaryKey(autoGenerate = true) val id: Int = 0.
Caso C: la consulta devuelve una lista puntual, no un flujo observable. Si queremos actualizar la
interfaz automáticamente, podemos devolver Flow<List<Alumno>>.
9. Buenas prácticas y errores frecuentes
 No ejecutar operaciones de base de datos en el hilo principal.
 No crear una instancia nueva de la base de datos en cada recomposición de Compose.
 No confundir una entidad con el DAO: una representa los datos y el otro las operaciones.
 No olvidar actualizar la versión y definir migraciones cuando cambie el esquema.
 No borrar ni recrear una base de datos en producción simplemente para evitar escribir una
migración: eso puede hacer perder información.
 Mantener la lógica de negocio fuera de los componentes visuales.
 Usar claves estables en listas de Compose cuando los elementos tienen identificadores.
